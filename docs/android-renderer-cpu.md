# CPU рендерера в гонке: Poco, 26 октября 2026

Снята текущая установленная сборка, без переустановки и изменения качества,
диагностики или алгоритмов. После короткого Home/возврата пользователь попросил
продолжать на нагретом телефоне. Скриншот подтверждает гонку.
PID 12611, renderer TID 23923. Запись примерно 10:34:05–10:34:51 MSK:
`cpu-clock`, 1000 Hz, DWARF callchains, clockid monotonic, 45 секунд.
37 678 сэмплов, lost=0; около 37,68 секунд sampled CPU, то есть примерно
84% одного ядра за запись. Это другой интервал, чем исходные 89,25% PERF5.

Символы сверены по build ID установленного ELF:
`22d47a1bded78c6dce977c846003518f527a42da`, соответствующий unstripped ELF
из `android/app/build/intermediates/cxx/Debug/215p5t4j/obj/arm64-v8a/`.
Другой каталог `3e6z6f5v` имеет иной build ID и не использован для анализа.
Внутренние функции Mali лишены имён; атрибуция API сделана по возвратам
в вызывающий код приложения и DWARF line information, не по догадкам об адресах.

## Разделение sampled CPU без двойного счёта

| Категория | Доля |
|---|---:|
| Поддерево Mali, включая вызванные им libc/syscalls | 37,55% |
| Vulkan-путь приложения и Android framework вне Mali | 27,70% |
| Разбор Xbox-команд и подготовка batch/геометрии до Vulkan | 23,00% |
| Текстурный путь приложения вне Mali | 6,10% |
| Логирование, включая его libc/syscalls | 5,04% |
| Остальное | 0,61% |

Правила: сначала выделено логирование, затем любой стек с `libGLES_mali.so`,
затем текстурный путь, затем Vulkan draw/flip/Android adapters, затем
`draw_primitive`/`draw_inline*`/`nv2a_pb_*`. Поэтому загрузка vertex/index/uniform
буферов внутри Vulkan backend относится к его категории; это граница слоя,
а не утверждение, что вся подготовка геометрии находится в executor.
Часы PERF5 тоже включены в соответствующие категории, а не вычтены.
Частично оборванные стеки могут влиять на классификацию.

Встречаются примерно 2257–2926 игровых draw на кадр; instancing=0.
Никакого общего исчезновения стоимости pushbuffer после NEON здесь нет,
но крупнейшее самостоятельное направление — per-draw Vulkan/driver work.
В `vk_draw_raw_impl` также сэмплируется поиск pipeline: hash всего `PipeKey`
и сравнения cache keys. Присутствие этого пути не означает компиляцию pipeline.

Следующий кандидат для отдельного эксперимента — уменьшение повторной
подготовки и записи одинаковых состояний и vertex bindings, а также
allocation/update дескрипторов на каждый draw. Сначала нужны счётчики
повторений и проверка lifetime ресурсов. Доля `vkCmdDrawIndexed` внутри Mali
не доказывает допустимость объединения draw: порядок и состояния должны
сохраняться. Переключение на native push descriptors этим профилем не обосновано.

## Отдельно кадры 52–67 мс

Часы CLOCK_REALTIME и CLOCK_MONOTONIC сопоставлены маленькой read-only
утилитой на телефоне; повторная проверка offset отличается менее чем на
0,2 мкс. Конец интервала берётся из millisecond timestamp `[hitch]`, начало —
конец минус округлённое время кадра. Поэтому границы приблизительные: как
минимум около 1 мс неопределённости, плюс задержка между замером и логом.
Это интервалы между внутренними flip callbacks, не SurfaceFlinger presentation.
Нельзя точно восстановить стеки четырёх старых кадров из предыдущей записи:
стеков в тот момент не снимали. Ниже новые кадры того же диапазона.

В кадре 12617/67 мс текстуры заметны: 14 мс. В остальных в этом диапазоне
обычно 0–5 мс. На кадрах с малыми текстурными затратами в стеках остаются
обычные draw/descriptor/command paths, а не новый массовый texture decode
или shader compile. В hitch-строках этих кадров programs compiled=0.

Около половины суммарного wall-интервала этих кадров не объясняется sampled
CPU рендерера. Это сильный повод дополнительно снять sched_switch/sched_wakeup
и waits/fence/submit в общей временной шкале. CPU-clock sampling не показывает
стек спящего потока и не различает вытеснение, ожидание executor, GPU/driver
и блокировку логирования. Нельзя приписывать весь недостающий wall Mali
или нагреву. Sampling и сбор скриншота также могли возмутить сцену; это
диагностический профиль, не A/B измерение FPS или причин троттлинга.
