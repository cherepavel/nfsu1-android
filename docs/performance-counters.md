# Лёгкие счётчики тормозов Android

В этой диагностической версии счётчики включены по умолчанию. Каждый поток
хранит собственные суммы в TLS, без общего mutex, регистрации потоков или
записи истории событий. Примерно раз в 5 секунд активный поток пишет одну
строку `[PERF5]` и до четырёх строк `[PERFK]` в `nfsu1.log`. Роли: `main`, `renderer`, `apu`, остальные —
`worker`; различать рабочие потоки по `tid`.

После самостоятельной сборки и установки перед запуском:

```bash
adb shell setprop debug.nfsu.diagnostics 0
adb shell setprop debug.nfsu.gil_eager 1
adb shell setprop debug.nfsu.perf 1
adb shell am force-stop org.nfsu.android
adb shell am start -n org.nfsu.android/.LauncherActivity
```

Открыть проблемное меню или гонку, воспроизвести тормоза 30–60 секунд,
затем забрать полный журнал до следующего перезапуска:

```bash
adb pull /sdcard/Android/data/org.nfsu.android/files/nfsu1.log poco-perf.log
```

Стартовая строка `[ANDROID] performance counters=1` подтверждает включение.
`debug.nfsu.perf 0` с полным перезапуском выключает измерения. Пустое свойство
в этой версии означает включение. Предыдущий APK сам не обновляется: нужна
новая сборка из изменённых исходников.

## Чтение строки

- `window_ms` — реальное время с предыдущей сводки данного потока;
- `cpu_ms` — CPU-время всего этого потока за окно, включая код вне замеров;
- каждое поле `имя=число/сумма/максимум` — число завершённых операций,
  суммарная длительность и самая долгая операция в миллисекундах.

| Поле | Измеряемый участок |
|---|---|
| `gil_wait` | Вход в GIL, включая mutex очереди, ожидание билета и служебную работу |
| `gil_cs` | От начала входа в GIL до захвата mutex очереди, включая получение приоритета |
| `gil_queue` | Для вставших в очередь: от захвата mutex при входе до передачи своего билета |
| `gil_handoff` | От передачи своего билета предыдущим владельцем до выхода из цикла ожидания с mutex очереди |
| `spin_wait` | Ожидание повторного входа в GIL после RECOMP_SPIN_HINT |
| `spin_total` | Время SwitchToThread и повторного входа после RECOMP_SPIN_HINT |
| `preempt_wait` | Ожидание повторного входа в GIL после RECOMP_PREEMPT |
| `preempt_total` | Время SwitchToThread и повторного входа после RECOMP_PREEMPT |
| `gil_held` | Время от получения GIL до его освобождения; это не чистое CPU-время |
| `apu_wait` | Гостевой вход через `mcpx_apu_lock_guest`, включая ожидание mutex APU |
| `apu_work` | Полная обработка `se_frame` в потоке APU, без throttle и последующего ожидания |
| `pb_work` | Разбор одного поступившего участка Xbox pushbuffer, включая вызовы рендерера |
| `vk_draw` | Обработка draw_raw: подготовка ресурсов, pipeline/descriptor/command calls |
| `vk_flip` | Полный callback flip, включая acquire, submit, present и следующий frame_begin |
| `vk_fence` | Ожидания frame fence при повторном использовании слота и заполнении ring |
| `vk_acquire` | CPU-вызов vkAcquireNextImageKHR |
| `vk_submit` | CPU-вызовы отправки; для early-submit также vkEndCommandBuffer |
| `vk_present` | CPU-вызов vkQueuePresentKHR |

Суммы, кроме `cpu_ms`, измеряются монотонными часами и включают вытеснение
потока и внутренние ожидания драйвера. Они не являются GPU timestamps.
Метрики вложены: `pb_work` содержит работу Vulkan, `vk_flip` — часть других
Vulkan-метрик, `gil_held` может содержать `apu_wait`. Их нельзя складывать как
независимые части кадра или трактовать разность как точное время GPU.
`gil_cs + gil_queue + gil_handoff` примерно разбивают `gil_wait`; оставшаяся
разница — служебная работа после получения билета. `gil_queue` включает
работу и задержки передачи всех предыдущих билетов, а не только полезную
работу держателей. `gil_handoff` включает сигнал, освобождение mutex прежним
владельцем, планирование получателя и повторный захват mutex; это не чистое
время планировщика. Сравнивать эти поля у всех потоков, особенно `main`.
Счётчики queue/handoff учитывают только входы с фактической очередью;
их число может быть меньше числа `gil_wait`/`gil_cs`.
`vk_draw` не включает все операции clear и декодирования Xbox-команд;
для полного участка CPU-исполнителя смотреть также `pb_work`.

Окна потоков не синхронизированы. Операция учитывается после завершения,
поэтому может пересекать границу окна; суммы иногда превышают `window_ms`.
Если поток завис внутри операции, сводка задержится до его следующего
безопасного места отчёта. Отсутствие строки не доказывает отсутствие нагрузки.
Сводка использует обычный stderr; хотя общей блокировки сборщика нет,
измерения и редкая запись лога тоже имеют стоимость. В APU сводка пишется
между обработками блоков, при ещё удерживаемой штатной блокировке APU.

Сначала нужны несколько строк всех ролей на одном проблемном участке.
Сама эта правка не меняет алгоритмы GIL/APU/Vulkan и не заявляет прирост FPS.

## Вызовы ядра, после которых поток возвращается в GIL

`[PERF5]` дополнительно содержит `resume_calls`, `resume_wait_ms` и
`resume_kernel_ms`: число измеренных возвратов из ядра, сумма ожиданий GIL
именно при этих возвратах и суммарное время самих вызовов ядра.

Следующие `[PERFK]` перечисляют четыре пары `(ordinal, caller)` с наибольшей
суммой ожиданий в том же окне и потоке:

- `ordinal` — номер Xbox kernel export;
- `caller` — гостевой адрес возврата, снятый до изменения стека bridge;
- `calls` — число возвратов в GIL после вызовов этой пары;
- `kernel_ms` — суммарное время внутри ядра, без последующего ожидания GIL;
- `wait_ms` / `wait_max_ms` — сумма и максимум ожидания GIL после этих вызовов.

Таблица на 128 пар фиксирована и находится в TLS. Если пар больше,
дополнительная строка `bucket=overflow` сообщает число и ожидания
неатрибутированных возвратов; эти значения входят в общие resume-суммы.
Рейтинг показывает только четыре места; остальные пары не исчезают из итогов.

Вызовы, которые сохраняют GIL (`kernel_call_keeps_gil`), в этот рейтинг не
входят. Входы GIL из poll/preempt, ISR/DPC и начального запуска также не
атрибутируются как возвраты из ядра. Разница между `gil_wait` и
`resume_wait_ms` показывает ожидания вне измеренных возвратов, с поправкой
на границы окон.

`kernel_ms` — монотонное wall-время, включая host wait, I/O и вытеснение.
Вложенные вызовы могут перекрываться; это не CPU-время. Малое среднее время
вызова само по себе не доказывает, что вызов безопасно выполнять под GIL.
После определения горячих пар требуется проверить их код и семантику.

Проверка самого хранилища на host:

```bash
cc -std=gnu11 -Wall -Wextra -Werror -pthread tests/android_perf_sites.c \
  -o /tmp/nfsu-perf-sites-test
/tmp/nfsu-perf-sites-test
```

Проверяются отдельные caller одного ordinal, дельта ожиданий без примеси
предыдущих вызовов, TLS-изоляция, overflow, выключенный режим и сброс окна.

## Разделение poll и preempt

Ожидания этих двух путей видны отдельно в `spin_wait` и `preempt_wait`.
Поля `*_total` включают также задержку добровольного host yield; их нельзя
складывать с `*_wait`. Число операций учитывает только реальные отпускания
GIL, а не вызовы при уже отпущенной блокировке. Preempt не учитывается
повторно как spin. Сумма `resume_wait_ms + spin_wait.sum + preempt_wait.sum`
должна объяснять основную часть `gil_wait.sum`; остаток — другие входы
и пограничные эффекты окон. Алгоритмы yield и guards ISR/DPC не изменены.

## Стадии обработки текстур Vulkan

В роли `renderer` добавлены следующие поля (число участков / сумма / максимум,
в миллисекундах). Они включаются штатным `debug.nfsu.perf`:

| Поле | Измеряемый участок CPU |
|---|---|
| `tex_hash` | Проверка содержимого гостевой текстуры и палитры; включает проверки неизменившихся текстур |
| `tex_image` | Создание VkImage, выбор/выделение и привязка памяти, view и запись начального barrier для кэшируемой текстуры |
| `tex_staging` | Выделение места в upload ring; включает возможное ожидание/submit при заполнении ring |
| `tex_decode` | Декодирование остальных форматов и unswizzle в ring, без DXT |
| `tex_dxt` | Декодирование DXT1/3/5 в BGRA при отсутствии прямой поддержки BC |
| `tex_upload` | CPU memcpy сжатых/линейных данных и запись команд копирования/barriers, отдельные участки одного счётчика |
| `tex_mips` | Запись GPU blit/barrier для mip-уровней декодированной кэшируемой текстуры |

`tex_decode` и `tex_dxt` не перекрываются. Это wall-время CPU, включающее
вытеснение потока; `tex_upload` и `tex_mips` не измеряют время исполнения GPU.
`tex_staging` может содержать вложенные `vk_fence`/`vk_submit`, поэтому их
суммы нельзя складывать. Число операций `tex_upload` не равно числу текстур.
Счётчики не покрывают отдельно создание render targets или динамические
cube maps из render surfaces.

После прежней строки `[hitch]` появляется `[texstage] frame N`, содержащая
суммы тех же стадий за этот кадр. Она выводится с тем же ограничением частоты,
а не для каждого draw/texture. `tex_hash` включает попадания в кэш, а прежнее
`textures (... ms)` учитывает только вызовы, завершившиеся загрузкой текстуры;
поэтому их суммы не обязаны совпадать. При `debug.nfsu.perf=0` стадийные
замеры отключены и значения `[texstage]` равны нулю.

Эта диагностика не распараллеливает декодирование и не меняет управление
памятью Vulkan. Она нужна для выбора работ, которые имеет смысл выносить
из последовательного рендерера.

## Блочное декодирование DXT

`nv2a_backend_decode_texture()` использует `d3d8_dxt_decode_image()` для
загрузки DXT1/3/5 в BGRA. Цветовые и alpha-палитры вычисляются один раз на
блок 4×4, затем записываются все видимые пиксели блока. Старый координатный
sampler для программной растеризации сохранён. Работа выполняется в прежнем
потоке; workers, очередей и изменения времени жизни гостевой памяти нет.

Дифференциальный тест сравнивает каждый пиксель с прежним sampler на
случайных изображениях трёх форматов, включая неполные блоки, невыравненный
source, прямоугольные изображения и 4096×1. Есть независимые эталонные
проверки прозрачного DXT1, alpha DXT3 и обоих режимов интерполяции DXT5,
а также guards вокруг выходного буфера.

```sh
cc -O2 -Wall -Wextra -Werror tests/dxt_bulk.c -o /tmp/nfsu-dxt-bulk-test
/tmp/nfsu-dxt-bulk-test
/tmp/nfsu-dxt-bulk-test --bench
```

ARM64 Android30, NDK 30, Poco X7 CPU 7, случайная текстура 256×256,
два чередующихся прохода по 40 распаковок:

| Формат | Старый sampler, мс/изображение | Блочный путь, мс/изображение |
|---|---:|---:|
| DXT1 | 2,064 / 2,001 | 0,314 / 0,326 |
| DXT3 | 2,208 / 2,295 | 0,303 / 0,293 |
| DXT5 | 3,067 / 2,925 | 0,367 / 0,372 |

Это синтетическая стоимость конкретной CPU-операции. Она не измеряет FPS,
создание VkImage, загрузку, mip blits, GPU или поведение очереди workers.

Один последовательный ручной заезд на каждый APK: число, размеры и форматы
поступивших текстур не идентичны, частоты и начальные температуры не
контролировались. Нельзя приписывать весь прирост flips/s только декодеру
или трактовать отношение сумм DXT как ускорение одинаковой нагрузки.
Суммы PERF5 асинхронны и могут пересекать границы интервала. Длительность
GPU этими таймерами не измерялась. Полной статистики времени каждого кадра нет.
В новом захваченном сеансе нет Fatal signal/FORTIFY/unsupported wait.
Один скриншот гонки показывает отрисовку сцены после установки; это не полная
визуальная проверка всех текстур. Длительная стабильность, загрузка/сохранение,
Home/resume и другие устройства не проверялись этим экспериментом.

Перед основным старым интервалом пойман кадр с 175,65 мс DXT и 78,70 мс
создания изображений. Это помогает выбрать две отдельные причины статтеров,
но не является парным замером с тем же кадром нового APK. После блочного
декодирования решение о workers следует принимать по остаточной стоимости
и размерам заданий: новый декодер не имеет состояния и может обрабатывать
независимые блоки, но безопасная публикация снимков данных и очередь работ
ещё не реализованы. Vulkan creation/command recording остаются на рендерере.

## Эксперимент: два CPU workers для DXT

Пул выключен по умолчанию. В одном APK сравниваются `debug.nfsu.tex_workers=0`
и `2`; свойство читается один раз. Перезапуск обязателен:

```sh
adb shell setprop debug.nfsu.tex_workers 2
adb shell am force-stop org.nfsu.android
adb shell am start -n org.nfsu.android/.LauncherActivity
```

`RECOMP_VK_TEX_WORKERS` из env имеет приоритет над свойством. Строка
`[TEXWORK] workers=2` подтверждает выбранный режим при первой подходящей
текстуре. Потоки называются `nfsu-dxt-0` и `nfsu-dxt-1`. Для отката установить
свойство `0` и полностью перезапустить приложение; базовый блочный декодер
остаётся синхронным. Android-эксперимент собирается обычным
`./gradlew assembleDebug lintDebug -Pnfsu.genOpt=-O2`.

Два workers делят одну DXT1/3/5-текстуру на непересекающиеся группы строк
блоков 4×4. Эксперимент берёт изображения от 65536 до 4194304 пикселей,
высотой не менее 8, с размерами не более 4096. Другие задания идут прежним
путём. Копия сжатых данных и декодированный CPU-буфер принадлежат пулу;
workers не читают гостевую память и не получают VkImage, command buffers,
JNI или адреса upload ring. Исходный снимок фиксируется вызовом memcpy,
а не атомарно относительно произвольных гостевых записей; существующий
порядок потребления текстуры рендерером сохранён.

Очередь ограничена одним изображением. Перед загрузкой рендерер ждёт обоих
workers и копирует их результат в ring. Это распараллеливание одной CPU
операции, а не подготовка будущих текстур/кадров: полезное перекрытие с
рендерером ограничено выделением места в ring. Предварительная подготовка
ещё не реализована. При отказе создания потоков или выделения буферов
используется синхронный путь. Буферы переиспользуются; максимальный объём
снимка и результата около 21 MiB плюс стеки/служебные данные потоков.
На выходе renderer pthread TLS-деструктор завершает работу и присоединяет
workers. При Home/возврате CPU-пул не зависит от presentation surface;
каждый tex_fill дожидается своего задания, включая отказ ring allocation.
Пул не поддерживает конкурентные begin/finish от нескольких владельцев.

Добавлены метрики:

| Поле | Смысл |
|---|---|
| `tex_snapshot` | Аллокация/рост snapshot/output и копирование сжатых данных |
| `tex_worker_wait` | Wall-время ожидания finish на рендерере, после ring allocation |
| `tex_worker_cpu` | Сумма thread CPU time двух workers на декодирование |
| `tex_worker_copy` | Копирование готового CPU-буфера в upload ring |

Они также добавлены в `[texstage]` для отдельных статтеров. Пуловые задания
не входят в `tex_dxt`; остальные синхронные DXT-текстуры продолжают входить.
`worker_cpu` нельзя складывать с wall-временем других стадий: workers работают
одновременно. Время начального создания потоков не входит в snapshot.
Собственные clocks пула собираются при включённом эксперименте даже с perf=0;
публикация PERF5 и стадийных сумм выключается штатным perf-переключателем.

Host/Android регрессия проверяет совпадение результата с блочным декодером,
изменение/освобождение исходной памяти сразу после begin, неполные и нечётные
строки блоков, reuse, отказ неподходящих заданий, запрет второй публикации и
уничтожение пула с активным заданием. Это не визуальный тест всех текстур.

```sh
cc -O2 -Wall -Wextra -Werror -pthread tests/texture_decode_pool.c \
  xboxrecomp/src/nv2a_vk/texture_decode_pool.c -o /tmp/nfsu-texture-pool-test
/tmp/nfsu-texture-pool-test
```

## Проверка draw batching и лишнего register scan

`debug.nfsu.draw_stats=1` (с полным перезапуском) включает существующие
сводки `[vk] per frame` каждые 300 flips; `RECOMP_DRAW_STATS` из env имеет

На текущем Android instancing по умолчанию выключен (`RECOMP_VK_INSTANCE=0`).
В исходном замере входные draw и игровые Vulkan calls совпали во всех десяти

## Покадровое разделение ожиданий рендерера

`[FRAMEWAIT]` в performance.log пишется при включённом perf на интервалах
между flip callbacks дольше 50 мс, максимум 30 строк за 10 секунд.
`begin_ns`/`end_ns` — CLOCK_MONOTONIC в той же точке, что измерение hitch;
`cpu_ms` — дельта CLOCK_THREAD_CPUTIME_ID данного потока. Эти границы позволяют
сопоставить лог с Perfetto без округления длительности до целых миллисекунд.

Поля `число/сумма/максимум` в мс:

- `idle_timeout`: полный вход в nv2a_thread_pause при неподвижном pushbuffer,
  включая mutex и condvar, законченный ETIMEDOUT;
- `idle_wake`: тот же участок, завершённый изменением поколения пробуждений;
- `idle_error`: тот же участок, прерванный другой ошибкой condvar;
- `pb_semaphore`: ожидание гостевого semaphore через nv2a_fence_wait;
- `vk_fence`, `vk_acquire`, `vk_submit`, `vk_present`: существующие Vulkan
  участки, отдельно накопленные между кадровыми границами.

Новые pb_* также видны в PERF5. Счётчики TLS: flag thread и renderer не
смешиваются. Кадровое накопление не сбрасывается пятисекундным poll.
Первый callback устанавливает границу и не публикует частичный кадр.
Предыдущий flip's submit/present попадает в следующий callback-интервал,
что соответствует измерению hitch. Только операции, завершившиеся между
границами, учитываются в строке; текущий callback ещё не завершён.
`pb_semaphore` может вызываться другим потоком — тогда он виден в его PERF5,
но не появится в кадровой строке рендерера.

Это wall-время участков, не чистое время сна и не GPU-время: вытеснение
внутри участка также учитывается. Разность wall и CPU нельзя автоматически
приписывать GPU. Новые замеры не меняют таймаут 1 мс, условия ожидания,
порядок команд, wake policy или Vulkan synchronization.

Проверка: host regression подтверждает сохранение кадра при PERF5 reset,
сброс только на границе кадра и выключенный режим. На macOS для существующего
syscall-based test используется `-Wno-deprecated-declarations`.
